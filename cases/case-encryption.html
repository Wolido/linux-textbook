加密的原理：对称、非对称与中间人

你在第二章连 SSH 的时候，终端弹出一行指纹让你确认；你在第八章调 HTTPS 接口的时候，浏览器地址栏显示了一把小锁。这两件事背后是同一套密码学逻辑在运转，但前两章忙着讲怎么用，没来得及停下来把原理说清楚。这篇补上。

对称加密：一把钥匙开一把锁

对称加密的想法很简单：加密和解密用同一把密钥。就像你家门口的防盗门，锁门和开门是同一把钥匙。你在电脑上把文件用 AES 算法加密，设一个密码；要解密的时候，输入同一个密码就行。这类算法速度很快，适合加密大量数据，比如一整段视频流或者一个几 GB 的数据库备份。

但它有一个绕不过去的问题：你打算怎么把这把钥匙安全地交到对方手里？

电视剧《潜伏》里的余则成在天津站潜伏的时候，这个问题天天摆在他面前。他和上级通消息，靠的是一本密码本——双方各持一份，发报时按本子上的规则加密，收报时反过来解密。但密码本怎么送到他手里？送的人可能被跟踪、被捕，密码本一旦暴露，之前所有的密电全都能被破译。这件事的本质到今天也没变：对称加密要求通信双方事先共享同一个秘密，而这个共享过程本身就是最大的风险点。你在小组里把 Wi-Fi 密码发到群里让大家用，这个动作正是对称加密的密钥分发问题。

非对称加密：公钥与私钥

1970 年代，密码学家提出了一个反直觉的方案：每人造一对密钥，而不是一把。一把叫公钥，可以满世界发；另一把叫私钥，死也不能给别人。这对密钥在数学上有关联，但从公钥反推私钥在计算上几乎不可行。

你可以把它想象成一个特殊的邮箱。任何人都能把信从投递口塞进去（用公钥加密），但只有拿着钥匙的人能打开邮箱取信（用私钥解密）。你把公钥公开在个人主页上，全世界都能给你写只有你能看的信。第二章里你用 ssh-keygen 生成的那对 ed25519 文件，正是这套逻辑的实例：id_ed25519.pub 是公钥，可以复制到任何服务器上；id_ed25519 是私钥，留在自己电脑上谁也别给。

邮箱比喻给了一个直观画面，但它没有说清楚公钥和私钥之间到底是什么关系。把这个画面往深想一步：用公钥加密之后，连加密时用的那个公钥自己都解不开。你锁上的东西，你没有钥匙打开，这和日常经验完全相反。日常的锁，锁门和开门是同一把钥匙；这里的锁，一把专门用来锁，另一把专门用来开，两把钥匙各走各的方向。反过来也一样：私钥"签名"的数据，只有公钥能验证。签名的意思是"我用私钥给这段数据盖了个戳"，任何人拿公钥一验就知道戳是不是真的，但没人能伪造这个戳，因为没有私钥。这就是"非对称"的含义：两个方向用不同的密钥，操作不可逆。

换个更贴切的比喻：把公钥想象成一种特殊的挂锁，谁都能"咔嗒"一声把它扣上，但扣上之后就打不开了。你把一堆这种开着的锁送给全世界，任何人想给你发消息，就拿起一把锁，把信锁进一个盒子里。盒子一旦锁上，连锁的那个人自己都打不开。只有你手里的私钥能开。和前面邮箱的"投递口"相比，这个比喻多了一层"操作不可逆"的方向感：锁的动作任何人都能做，解锁的动作只属于你。

这套机制能成立，根子在一个数学事实：从公钥推不出私钥。这对密钥在数学上确实是绑定的，公钥就是从私钥算出来的，但反推在计算上走不通。以 RSA 为例，背后的原理是对大整数做质因数分解极其困难：公钥里藏了一个巨大的合数，它等于两个大质数的乘积；要知道私钥就必须找出这两个质数各自是多少，而这件事即使用今天最快的计算机也要算到宇宙尽头。你把公钥贴到网上，谁都看得见，但谁也拿它没办法。

非对称加密完美解决了密钥分发问题，但它慢。加密同样的数据，RSA 比 AES 慢几百到上千倍。直接用它加密整个会话不现实。

两者配合：SSH 会话密钥的协商

非对称加密慢，对称加密快但怕泄密。怎么把两者串起来？你在第二章里每次 ssh 到服务器的时候，这两套机制就已经在配合工作了。

假设你敲下 ssh student@gpu-lab01。接下来的不到一秒里，你的 SSH 客户端和服务器之间发生了一次简短的非对称加密对话，目标只有一个：商量出一把临时的对称密钥。

第一步，服务器把自己的 host key 公钥发过来。就是第二章里你第一次连接时终端弹出一串十六进制指纹、问你 yes/no 的那把公钥。这把公钥存在服务器上，每个连它的人都能拿到。

第二步，你的 SSH 客户端在本地内存里随机生成一串数字。这个数是临时的，全世界只有你的电脑知道。你可以把它理解为会话密钥的"种子"。

第三步，客户端用刚才拿到的服务器公钥把这串随机数加密，密文发回服务器。非对称加密的意义就在这一步：公钥任何人都能拿到，但加密之后，连加密的人自己都解不开。只有持有对应私钥的服务器能把密文解开。服务器用自己的私钥一解密，拿到了和客户端一模一样的随机数。

到这一步，双方手上已经有了同一个秘密，但还不能直接用。第四步，客户端和服务器各自拿这个随机数，加上握手阶段交换的一些公开信息，一起喂进一个推导函数，算出一把"会话密钥"（session key）。这把会话密钥才是真正用来加密后续数据的。

此后你在这个 SSH 连接里敲的每条命令、服务器返回的每一行输出、你 scp 传的每一个文件，全用这把会话密钥做对称加密。对称加密快，你感受不到延迟。等你 exit 退出登录，双方把会话密钥扔掉。下次再 ssh 上来，整个协商从头来一遍，生一把全新的密钥。

这个流程说白了就是分工：在公共信道上安全地共享一个秘密，这是最难的一步，由非对称加密扛下来；加密整个会话的数据流，这是最重的一步，由对称加密扛下来。各做各擅长的事。顺带一提，SSH 实际采用的是 Diffie-Hellman 密钥交换，和上面简化的模型略有出入，但底层逻辑一样：用非对称手段在公共信道上协商出对称密钥。第八章讲 HTTPS 时提到的 TLS 握手，也是同一套思路。

但这里有一个前提不能忽略：你的 SSH 客户端得确认它拿到的 host key 公钥真的是目标服务器的。如果这一步被做手脚，后面所有步骤全都白费。这正是下一节要讲的中间人攻击。

中间人攻击：公钥交换的漏洞

非对称加密看起来很稳，但它有一个前提：你得确保你拿到的公钥真的是对方的，而不是某个中间人塞给你的假货。

想象你在咖啡馆连 Wi-Fi，旁边有人架了一台笔记本，伪装成咖啡馆的免费热点。你连上去之后访问 github.com，这个热点没有直接帮你连接真正的 GitHub 服务器，而是自己生了一对假密钥，用假公钥跟你的浏览器建立 HTTPS 连接，同时又用真公钥去连接 GitHub。你的请求先发到攻击者的机器上，它解密、看一眼、再用真密钥加密转发给 GitHub；GitHub 的响应同理，原路回来，攻击者全程透明地读取你所有的 Cookies 和密码。你的浏览器地址栏里甚至可能还挂着一把小锁。

这就是中间人攻击。它没有破解任何加密算法，它只是让你以为自己在跟正确的人说话。问题不处在加密环节，出在身份认证环节。

防御：SSH 的指纹与 HTTPS 的证书

解决思路是同一个：确认你拿到的公钥是真的。SSH 和 HTTPS 各走了一条路。

SSH 的做法很朴素。第一次连接时，客户端把服务器的 host key 指纹打印出来，问你是不是这台机器。你跟管理员贴在 wiki 上的指纹对一下，一致就输入 yes。确认之后，SSH 把服务器的公钥存进 ~/.ssh/known_hosts 文件。以后每次连接，客户端自动核对当前服务器出示的公钥跟文件里存的是否一致；如果变了，就弹出那行刺眼的 WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!。这相当于"第一次见面人工确认，之后机器自动验证"。第二章讲 SSH 时，你看到的那行指纹提示和 known_hosts 文件，背后的逻辑就是这个。

HTTPS 的规模决定了它不可能靠人工核对。浏览器面对的是全世界几亿个网站，每个用户都去跟站长核对指纹不现实。于是有了 CA（Certificate Authority，证书颁发机构）。网站站长花钱找 CA 给自己的公钥签一份证书，CA 用自己的私钥在证书上盖个章。你的浏览器出厂时内置了一份可信 CA 的名单，拿到证书后自动验证盖章是否有效、域名是否匹配、证书有没有过期。整个链条不需要你手动比对任何东西，但代价是你要信任这些 CA 不乱签证书。第八章里浏览器地址栏那把锁形图标的背后，就是这个证书链验证过程。

与本书的呼应

读完这篇，回头看第二章和第八章的某些细节，会有不一样的感受。

第二章里 ssh-keygen 生成的密钥对，不再只是"照做就行"的操作步骤，而是非对称加密中公钥和私钥的具体实例。第一次连接时让你确认的那串指纹，也不只是让人紧张的安全提示，而是 SSH 用人工信任锚点来防中间人攻击的关键机制。你下一次连接一个陌生服务器，看到那行 yes/no/[fingerprint] 的时候，知道自己在干什么。

同样，第八章 HTTPS 里的"TLS 协商"不再是抽象的一行描述，而是一套对称加密和非对称加密的接力流程。浏览器报警"证书不受信任"的时候，你也能判断：是 CA 那边出了问题，还是有人在中间捣鬼。

加密的原理并不神秘。对称快但怕泄密，非对称安全但慢，中间人钻的是身份认证的空子。三件事串在一起，就是 SSH 和 HTTPS 安全体系的核心骨架。

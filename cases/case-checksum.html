校验哈希：文件的指纹

第二章讲 wget 时我们提了一句：下载完文件，最好用 md5sum 或 sha256sum 校验一下官方公布的哈希值。当时没有展开，这篇延伸阅读就把这件事说清楚。

什么是哈希

哈希函数做的一件事，听起来很朴素：给它任意大小的数据，它还给你一串固定长度的字符。比如 SHA-256 算法，不管你扔给它一个三个字母的文本文件，还是一个 50 GB 的模型权重，输出永远是 64 位十六进制字符。

你可以把它理解成文件的指纹。指纹有两个关键性质，哈希也都有。第一，几乎不存在两个不同文件算出同一个哈希值的情况——就像没有两个人的指纹完全相同。第二，哪怕你只改动文件里的一个字符，算出来的哈希值也会面目全非，连一个字符都对不上。这叫“雪崩效应”：输入动一点点，输出全变。

也正因如此，哈希值常被用来回答一个简单的问题：我手里的这个文件，和对方手里的那个文件，是不是一模一样？不需要逐字节比对，只要比一下 64 个字符就够了。

用 md5sum 和 sha256sum 校验文件

来看一个实际例子。假设你刚用 wget 下载了一个公开数据集，下载完别急着解压，先算一下哈希：

student@debian:~/ai-materials$ sha256sum sample_data.zip
a3f5c8e2b1d4f7a9c6e8b2d5f3a1c4e6b8d2f5a7c1e3b6d8f2a4c7e9b1d3f5a8  sample_data.zip

然后打开数据集官网，找到页面上公布的 SHA-256 值，眼睛比一下，或者用搜索功能把你算出的值粘进去找一找。两个值一致，说明文件在传输中没有损坏，也没有被人动过手脚；不一致，就得重新下载，或者换一个来源。

md5sum 用法完全一样，只是输出短一些（32 位）。MD5 这个算法已经比较老，安全圈认为它不够可靠，容易被人为制造“碰撞”（两个不同文件算出同样的值）。所以现在更推荐用 sha256sum；不过很多老项目和数据集站还沿用 MD5，官方给哪个，你就用哪个。

如果你下载的不止一个文件，手工比对就很烦。很多项目会发布一个校验文件，比如 SHA256SUMS，里面每行是“哈希值 + 空格 + 文件名”。把它也下载下来，和文件放同一个目录，然后：

student@debian:~/ai-materials$ sha256sum -c SHA256SUMS
sample_data.zip: OK
large-model.pth: OK

-c 是 check 的意思，它会自动逐项校验，哪个文件对不上会直接标红 FAILED。课题组从 Hugging Face 拉模型、从材料数据库拉批量数据时，这个方法能帮你一次确认几十个文件的完整性。

哈希不只是校验

你以后会反复见到哈希，它远不止“下载后校对”这一个用途。

最显眼的是 Git。第五章会讲，Git 用一串哈希值标识每一次提交——你在终端里看到的那串 1a2b3c4，其实就是提交内容的哈希前缀。内容变，哈希就变，所以哈希值天然适合当“版本编号”。

再比如密码存储。正经的系统从来不保存你的明文密码，只保存密码的哈希值；你登录时，系统把你输入的密码再算一遍哈希，两个哈希一致就放你进去。这样即使数据库泄露，攻击者拿到的也只是一堆哈希，倒推不出原文。这里用的哈希算法和校验文件的是同一族思路，只是还要加“盐”等额外手段，细节就不展开了。

还有一些工程用途：网盘和同步工具用哈希判断文件是否重复，只存一份内容；IPFS 这类内容寻址系统干脆用哈希当文件的“地址”。可以说，现代软件到处都靠哈希来回答“这两个东西是不是同一个”。

什么时候该用

回到最实际的问题：什么时候值得花这十几秒？

几种情况强烈建议校验：一是下载大模型权重、公开数据集、系统 ISO 镜像这类又大又重要的文件。几个 GB 的文件走一趟网络，中途丢包、磁盘出错并不罕见，一个坏字节的模型可能让训练跑出莫名其妙的 NaN。二是从非官方源下载时——镜像站、论坛附件、陌生人给的链接，这些地方文件被替换或夹带私货的风险真实存在。之前学过的 XZ Utils 后门事件就是前车之鉴（见延伸阅读《XZ Utils 后门事件》）。

反过来，日常下个几 MB 的论文 PDF、配置文件，没必要每次都校。校验的成本很低，但也不是零，把力气留给真正重要的文件就好。
